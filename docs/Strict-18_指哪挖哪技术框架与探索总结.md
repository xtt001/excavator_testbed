# Strict-18：“指哪挖哪”技术框架与探索总结

## 结论

- 任务状态：最终技术框架已经确定，“ACT 是否真的读取目标并改变 Unity 中的运动”这个关键前提也得到了正向证据。完整的“指哪挖哪”还没有实现；当前正在进入最关键的 Dig 单铲土体效果验证。
- 直接判断：这一轮非常有价值。它把核心疑问从“目标 token 有没有作用”推进到了“不同 Dig 目标能否产生正确的入土位置、深度、出土位置和土体移除效果”。
- 安全与影响：所有在线实验都保留了接触停止、独立策略缓存、不重试、默认 legacy 时序聚合和原安全阈值。生产默认行为没有改变。
- 下一步：完成当前正在开发的 Dig 单铲位置 A/B 实验。若两个目标能在相同起点下挖到不同且正确的位置，才进入 Return→Dig 集成和多铲地形闭环。

## “指哪挖哪”最终采用的技术框架

可以把它理解成“规划员、驾驶员、安全员、测量员”四个角色：

```text
目标地形 + 当前实际地形
        ↓
规划员：决定下一铲应该从哪里入土、挖多深、从哪里出土
        ↓
目标管理：锁定这次目标，保证 Return 和下一次 Dig 使用同一个目标
        ↓
流程调度：安排 Return → Dig → Carry → Dump
        ↓
驾驶员 ACT：根据四路图像、机械状态和目标，直接输出四轴控制动作
        ↓
独立安全员：预测短期运动，检查墙、硬底、碰撞、高力、限位和卡死
        ↓
执行动作
        ↓
测量实际轨迹、接触、载荷和土体变化
        ↓
用“目标与实际的差”更新剩余地形，再规划下一铲
```

这里最重要的边界是：

- Planner 负责决定“挖哪里”，不生成摇杆动作或整条关节轨迹。
- ACT 负责“怎么操纵挖机到那里”，直接输出 swing、boom、stick、bucket 四轴动作。
- 历史专家关节轨迹只用于训练支持范围、安全诊断和标定，不作为在线控制轨迹。
- 安全系统独立于 ACT。ACT 即使给出危险动作，安全链仍有最终停止权。
- `DesiredCutGoal` 表示这次想挖成什么样；`AchievedCutOutcome` 表示最终实际挖成什么样。两者不能混为一谈。

## 为什么这个框架有希望实现“指哪挖哪”

“指哪挖哪”至少包含三层能力：

1. **指得清楚**

   Planner 给出的不是模糊的“去挖土”，而是包含入土点、出土点、方向、深度、载荷和目标区域的明确目标。

2. **动作会随目标改变**

   ACT 的输入中直接包含目标。相同图像、相同机械状态下，只换目标，ACT 应给出不同动作。这一点已经得到离线和 Unity 在线证据。

3. **实际挖掘结果能被纠正**

   每铲完成后测量实际挖掉的土。如果偏离目标，Planner 根据剩余地形重新计算下一铲，而不是机械地重复预先写好的路径。

因此，这套系统不是“播放一条专家轨迹”。它是一个不断执行、测量、纠偏的闭环。只要 ACT 能稳定把目标转成正确的土体效果，误差就可以通过后续铲次逐步消除。

## 这一轮的探索过程

### 1. 先分清“能连续运行”和“挖得准确”

旧系统曾完成十铲连续流程，但入土、出土和深度误差都较大。Strict-18 后来恢复到九次 Dump，也只说明流程恢复到了较高完成度。

这些结果证明挖机能够持续执行多个 primitive，却没有证明 Planner 指定的位置真的被准确执行。由此确定：继续追求“再多跑一铲”不能解决核心问题，必须验证目标是否真正控制动作和土体效果。

### 2. 放弃“Planner 先生成完整关节轨迹”的方向

早期思路曾把目标转换成完整 qpos 路径，再考虑让 ACT 跟踪。审查代码后确认，现有 ACT 本来就是“观察 + 目标 → 动作”的直接策略，专家路径并不是它的输入。

最终选择保留 ACT 的学习控制能力，让 Planner 只负责目标。这样 ACT 可以根据实时图像、接触和机械状态调整动作，不会被一条预先生成的固定轨迹绑死。

### 3. 离线验证 ACT 是否读取目标

阶段 A 固定所有观测、图像、机械状态、checkpoint 和缓存，只替换目标：

- Dig：10 段中有 9 段稳定改变动作；1 段仍超出正式支持范围。
- Return：经过更合适的支持范围检查后，9 段中有 7 段稳定响应。
- Carry/Dump：额外注入 Dig 目标后动作完全不变，说明目标没有错误泄漏到无关阶段。

这一步证明了模型内部确实使用目标，但仍是录像上的离线反事实推理，不能说明 Unity 中会沿正确方向运动。

### 4. 找到 Return 两段失败的真实原因

ACT 每次预测未来 100 帧动作。默认 legacy 派发会把过去多个预测块混合起来，以减少抖动。

两段 Return 中，最新动作块对目标的响应率分别达到约 99.3% 和 100%，混合历史动作块后下降到约 77.4% 和 71.9%，低于冻结的 80% 门槛。

因此问题不在 token 没输入、图像错位或 cache 没清，而是新目标的影响被旧预测稀释了。我们没有降低门槛，也没有把 latest 变成默认策略。

### 5. 历史姿态复现路线暴露了基础设施问题

最初计划用 F1/F2/N1/N2 四个历史 Return 姿态做 16 臂在线矩阵。实际发现：

- 历史 HDF5 没保存当时物理 qpos 归一化配置的 SHA 和范围；
- 历史非零速度和土体内部状态无法恢复；
- Unity `REALIGN` 的目标虽然写进 lock，真实 readback 却没有到达请求姿态；
- 沿物理路径摆姿时还可能碰到 `Dig_ZMin_Board`。

所以这条路线不能称为历史物理状态复现，也不能用于判断 ACT 是否响应目标。

这段工作仍然有价值。它排除了一个错误实验前提，也让后续实验明确区分“历史录像附近的姿态种子”和“可验证的当前 Unity 起点”。

### 6. RESET 起点证明有响应，但安全窗口太短

随后改用当前 Unity RESET 后的真实状态，不再恢复历史姿态。

四臂实验中，legacy 和 latest 的 original/alternate 轨迹都在接触前分开，但约 20–36 步就发生土体接触。结果只能说明“目标开始影响运动”，无法判断完整 Return 是否正确。

相机也出现过极小的像素抖动。进一步测试发现，这些像素差只造成百万分之一量级的动作变化，远低于冻结阈值。因此实验合同从“每帧像素完全相同”改成了更实际的“图像变化不能显著改变同目标动作”。

### 7. 自动选姿失败后，改用人工选择的运行时临时姿态

自动候选路线仍依赖旧 `REALIGN`，部分候选在摆姿过程中碰板，其余也未到达请求姿态。于是停止自动选择，改为：

- 先生成九个无动作四视角预览；
- 由操作者明确选择 `C01`；
- 每臂进入独立 Play Mode；
- 使用仅在当前 Play Mode 存在的 runtime pose override；
- 不调用 `REALIGN`，不保存场景；
- original/alternate 分别重新建立同一起点。

这一步终于形成了有效的 Unity 在线因果诊断：

- 两臂 qpos、qvel 和 107D 起点误差均为 0；
- policy 和 temporal cache 完全独立；
- Unity 确认收到 535 条非零 STEP；
- 共同的 250 帧接触前窗口中，第 10 帧开始满足持续轨迹分离；
- 最大铲尖距离约 0.996 米；
- original/alternate 分别在第 283/250 帧首次接触土体并停止；
- alternate 曾进入自己的目标包络，original 没有。

这证明：**默认 legacy 策略在一个可验证一致的 Return 起点上，会因为目标不同而产生不同的真实 Unity 轨迹。**

它还没有证明两个目标都被正确完成，所以 latest 没有继续运行，默认策略也没有改变。

## 现在处于最终目标的什么位置

| 能力层级 | 当前状态 |
|---|---|
| 明确“谁决定目标、谁输出动作、谁负责安全” | 已完成 |
| 离线证明 ACT 会读取 Dig/Return 目标 | 已完成，但有支持范围和 Return 聚合限制 |
| Unity 中证明只换 Return 目标会改变真实轨迹 | 已完成一次低证据诊断 |
| 证明 Dig 会在指定位置入土、达到指定深度并从指定位置出土 | 尚未实际运行 |
| 证明目标区域的土体确实被按要求移除 | 尚未实际运行 |
| Return 使用同一目标为下一次 Dig 正确准备姿态 | 尚未集成验证 |
| 根据挖后地形自动规划下一铲 | 尚未做有界多铲闭环 |
| 正式十铲“指哪挖哪”验收 | 尚未开始 |

按原来的 A–F 路线看：

- 阶段 A 的目标敏感性诊断已经完成。
- Return 的额外 Unity 因果诊断已经完成。
- 当前正在阶段 B/C：Dig 目标与结果合同、执行器遥测已经开始落地，安全预演和一次性双臂 runner 仍在整合。
- 阶段 D 的真实 Dig 土体效果 A/B 还没有执行。
- 阶段 E 多铲 residual 闭环和阶段 F 正式十铲验收都还没有开始。

所以现在处于“已经证明方向盘会听目标，但还没证明铲斗能把指定位置的土挖成指定结果”的位置。

## 这一轮到底有没有价值

有，而且价值很明确。

它没有直接交付生产版“指哪挖哪”，但解决了三个基础问题：

1. **证明目标不是摆设**

   改变目标确实会改变 ACT 动作，并进一步改变 Unity 中的实际轨迹。系统不需要回到 exact-tuple 或固定专家路径方案。

2. **把不同故障分开了**

   现在可以区分：

   - 模型没有读目标；
   - 时序聚合削弱目标；
   - Unity 起点没有真正复现；
   - 相机只有无害抖动；
   - 轨迹改变但目标几何不正确；
   - 几何正确但土体效果不正确。

3. **建立了可信的实验基础设施**

   包括相同起点检查、独立 policy/cache、无保存 Play Mode、runtime-only 姿态、接触即停、no-overwrite、四路视频、铲尖轨迹、结束清理和默认 RESET 回归。

最核心的不确定性已经发生变化：

> 以前的问题是“ACT 到底有没有读取目标？”

现在的问题是：

> “ACT 产生的目标相关运动，能否准确落到 Dig 的入土点、深度、出土点和目标土体区域？”

这正是当前 Dig 单铲位置 A/B 实验要回答的问题。
