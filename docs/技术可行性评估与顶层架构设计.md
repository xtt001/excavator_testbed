## 2. 宏观可行性判定

### 2.1 结论

**技术路线宏观可行，但存在一个硬性前提条件和三个需主动管理的风险。**

### 2.2 硬性前提：土体仿真可用性

当前路线的核心假设是"仿真先行"，但 MuJoCo 无法模拟土体。如果无法在 M3（4-8 周）内接入至少一种可用的土体仿真后端，整条"挖掘循环"的训练与评测将停留在刚体代理任务上，与真实目标存在不可弥合的 gap。

**可行性判定**：


| 候选方案                   | 物理真实性              | 工程接入成本           | 授权与部署    | 综合可行性  |
| ---------------------- | ------------------ | ---------------- | -------- | ------ |
| Project Chrono DEM     | 高（颗粒力学成熟）          | 中（需自建挖掘机刚体与耦合接口） | 开源 BSD   | **首选** |
| Isaac Sim + Omni PhysX | 中高（PBD 粒子，非严格 DEM） | 高（平台重，GPU 强依赖）   | 免费但闭源    | 备选     |
| AGX Dynamics           | 最高（工业级）            | 中高               | 商业授权，成本高 | 条件储备   |
| Taichi MPM             | 高（连续介质）            | 很高（需自行耦合刚体）      | 开源       | 研究储备   |


**建议**：以 Chrono DEM 为首选土体后端，在 M2 末启动 POC，M3 完成最小可录制任务。同时保持 MuJoCo 作为快速策略迭代后端不变。

### 2.3 三个主要风险

#### 风险 1：刚体代理任务与真实挖掘的 sim-to-real gap

- **本质**：在 MuJoCo 上训练的策略是在"无土阻力、无颗粒流动、无堆形变化"条件下习得的，迁移到有土体的环境时，动力学分布偏移很大。
- **缓解**：MuJoCo 阶段的策略结构（ACT + action chunking）和工程流水线（录制/训练/评测/Guard）仍然有效；迁移到 Chrono 后重新采集数据即可，训练侧代码无需修改。因此 MuJoCo 阶段的工程投入不浪费。
- **残余风险**：中。取决于 Chrono 接入后的数据采集效率与仿真实时性。

#### 风险 2：ACT 对长时域多阶段任务的适用性

- **本质**：ACT 论文验证的是桌面级短时域操作（~400 步，单一阶段）。完整挖掘循环（入土→铲取→回转→卸料→回位）步数更长，且阶段间动力学差异大。
- **缓解**：引入分阶段策略架构（Phase Router + 每阶段独立 ACT），每个 ACT 只负责一个阶段的短时域执行，降低单策略负担。
- **残余风险**：中低。阶段识别本身可用规则或简单分类器实现，不依赖 ACT 的泛化能力。

#### 风险 3：仿真后端切换的工程成本

- **本质**：当前代码与 MuJoCo (dm_control) 深度耦合——`physics.named.data.qpos`、`physics.render()`、`physics.data.contact` 等调用散布在 `sim_env.py`、`ee_sim_env.py`、`scripted_policy.py` 中。
- **缓解**：在 M1 完成统一环境工厂接口 (`SimBackend` ABC)，将 MuJoCo 实现封装为 `MuJoCoBackend`，后续新增 `ChronoBackend` 只需实现同一接口。
- **残余风险**：低。这是纯工程工作，设计得当后一次性投入。

### 2.4 可行性总评

```
整体可行性：  ★★★★☆ (有条件可行)
                    └── 条件：土体仿真后端在 M3 前完成接入

分项可行性：
  策略框架 (ACT)    ★★★★★  已验证，架构成熟
  工程流水线         ★★★★☆  闭环已通，需补接口层与评测
  仿真快速迭代       ★★★★★  MuJoCo 侧成熟
  土体仿真          ★★★☆☆  候选方案明确，但工程落地待验证
  分阶段任务         ★★★☆☆  思路清晰，实现待推进
  安全与约束         ★★★★☆  概念简单，工程量可控
```

## 3. 顶层架构设计

### 3.1 系统分层总图

```

├─────────────────────────────────────────────────────────────────┤
│                     阶段路由层 (Phase Router)                    │

│  输出: 当前阶段标签 + 阶段子目标 + 切换信号                        │
│  Baseline: 规则 FSM → 后续可接学习分类器                          │
├─────────────────────────────────────────────────────────────────┤
│                     执行层 (Execution / ACT)                     │
│  输入: S_t + 阶段子目标                                           │
│  输出: 短时动作块 action_chunk (4-DOF, chunk_size 步)             │

## 4. 模块规格

### 4.1 仿真后端层 (Sim Backend)

```
模块名：    SimBackend
职责：      封装物理引擎，提供统一的 reset/step/render 接口
当前实现：  MuJoCo (dm_control)，与 sim_env.py / ee_sim_env.py 深度耦合

能力边界：
  ✓ 刚体多体动力学、关节控制、碰撞检测
  ✓ 高速迭代（MuJoCo 单步 <1ms）
  ✗ 无颗粒/连续介质土体
  ✗ 无变形地形
  ✗ 无液压回路仿真

输入：
  action: np.ndarray, shape=(action_dim,)   # 关节目标位置
  config: SimConfig                          # 后端参数、场景参数、随机化范围

输出：
  obs: dict
    qpos:      np.ndarray, shape=(state_dim,)      # 关节位置
    qvel:      np.ndarray, shape=(state_dim,)      # 关节速度
    images:    dict[str, np.ndarray(H,W,3,uint8)]  # 各相机渲染
    env_state: np.ndarray                           # 环境物体状态（可选）
    contacts:  list[ContactInfo]                    # 接触信息（可选）
  reward: float
  done:   bool

统一接口 (ABC)：
  class SimBackend(ABC):
      def reset(self, config: SimConfig) -> dict: ...
      def step(self, action: np.ndarray) -> tuple[dict, float, bool, dict]: ...
      def render(self, camera_name: str, height: int, width: int) -> np.ndarray: ...
      def get_contacts(self) -> list[ContactInfo]: ...
      @property
      def dt(self) -> float: ...

Baseline 实现：
  ├── MuJoCoBackend        — 当前代码重构封装，M1 完成
  ├── ChronoBackend        — Chrono DEM 颗粒 + 挖掘机刚体，M3 目标
  ├── IsaacSimBackend      — 备选，M4+ 视条件推进
  └── AGXBackend           — 条件储备，视授权推进

迁移原则：
  训练侧 HDF5 结构不变，仅替换后端实现。
  字段约束：qpos/qvel 语义一致，images 相机名一致。
```

### 4.2 状态接口层 (State Interface)

```
模块名：    StateInterface
职责：      将仿真/实机原始观测转化为结构化状态 S_t，供策略与评测统一消费
当前实现：  不存在，策略直接读取 raw qpos

能力边界：
  V1（M1 目标）：
    ✓ 关节状态提取与归一化
    ✓ 末端/铲斗关键位姿计算（正运动学）
    ✓ 任务阶段标签（由 Phase Router 写入）
    ✓ 基础置信度占位
  V2（M3+ 目标）：
    ✓ 土体特征估计（来自仿真后端扩展字段）
    ✓ 传感器健康度

输入：
  raw_obs: dict                # 来自 SimBackend 的原始观测
  task_context: TaskContext     # 当前任务配置（如挖点、卸点坐标）

输出 (S_t V1)：
  machine_state:
    joint_pos:   np.ndarray(4,)    # 归一化关节位置
    joint_vel:   np.ndarray(4,)    # 归一化关节速度
    ee_pos:      np.ndarray(3,)    # 铲斗尖端世界坐标
    ee_quat:     np.ndarray(4,)    # 铲斗姿态四元数
  task_phase:    str               # APPROACH / DIG / SCOOP / LIFT / SWING / DUMP / RETURN
  sub_goal:      np.ndarray        # 当前阶段子目标（位姿或关节目标）
  confidence:
    perception:  float             # [0,1]，感知置信度
    map_complete: float            # [0,1]，地图完整度
  images:        dict[str, ndarray] # 原始图像透传（ACT backbone 消费）

Baseline：
  直接从 SimBackend 输出提取，正运动学用 MuJoCo 的 site_xpos 或自行实现。
  阶段标签由规则 FSM 写入，不需要额外模型。
```

### 4.3 阶段路由层 (Phase Router)

```
模块名：    PhaseRouter
职责：      识别当前作业阶段，管理阶段间切换，为执行层提供阶段子目标
当前实现：  不存在，当前为单一策略覆盖全过程

能力边界：
  V1：规则 FSM，基于关节位置 / 接触状态 / 时间步判断阶段
  V2：学习分类器（如 MLP/Transformer 分类头），基于 S_t 特征判断

阶段定义（挖掘循环）：
  ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐
  │ APPROACH│───→│   DIG   │───→│  SCOOP  │───→│  LIFT   │
  └─────────┘    └─────────┘    └─────────┘    └─────────┘
                                                    │
  ┌─────────┐    ┌─────────┐    ┌─────────┐         │
  │ RETURN  │←───│  DUMP   │←───│  SWING  │←────────┘
  └─────────┘    └─────────┘    └─────────┘

输入：
  S_t: StructuredState
  task_plan: SubGoalSequence    # 来自任务层的子目标序列

输出：
  phase_label:  str             # 阶段枚举
  sub_goal:     np.ndarray      # 当前阶段的目标位姿/关节目标
  switch_signal: bool           # 是否触发阶段切换
  progress:     float           # 当前阶段进度 [0,1]

Baseline：
  规则 FSM，切换条件示例：
    APPROACH → DIG:   铲斗尖端 z < dig_depth_threshold
    DIG → SCOOP:      水平位移 > scoop_distance 或阻力超限（V2 才有）
    SCOOP → LIFT:     bucket 关节角度达到收斗阈值
    LIFT → SWING:     boom 关节角度达到抬升阈值
    SWING → DUMP:     swing 角度接近卸点方向 ± tolerance
    DUMP → RETURN:    bucket 打开且保持时间 > t_dump
    RETURN → APPROACH: swing 回到挖点方向 ± tolerance

  后续可替换为学习分类器，训练数据从标注的 episode 中获取。
```

### 4.4 执行层 (ACT Policy)

```
模块名：    ACTExecutor
职责：      消费结构化状态与阶段子目标，输出短时动作块
当前实现：  ACT (CVAE)，PACT/policy.py + PACT/detr/

能力边界：
  ✓ 短时域（chunk_size=100 步 × 0.02s = 2s）动作生成
  ✓ 图像 + 本体感觉联合推理
  ✓ 动作时序平滑（action chunking + temporal aggregation）
  ✓ 训练稳定（CVAE + L1 loss + KL regularization）
  ✗ 不承担语义推理
  ✗ 不承担长时域规划
  ✗ 不承担安全约束

模型架构：
  Encoder (CVAE):
    input:  [CLS] + qpos_embed + action_seq_embed
    output: μ, logσ² → latent z (32-dim)
    arch:   4-layer Transformer Encoder

  Decoder:
    input:  image features (ResNet18) + qpos + latent z
    output: action_chunk (num_queries × state_dim)
    arch:   7-layer Transformer Decoder
    
  参数量：~30M（ResNet18 约 11M + Transformer 约 19M）

输入：
  qpos:     torch.Tensor(B, state_dim)                    # 归一化关节状态
  image:    torch.Tensor(B, num_cam, 3, 480, 640)         # 归一化图像
  actions:  torch.Tensor(B, chunk_size, state_dim) | None # 训练时提供

输出：
  训练时: loss_dict = {l1, kl, loss}
  推理时: action_chunk: torch.Tensor(B, chunk_size, state_dim)

当前超参数：
  chunk_size (num_queries): 100
  hidden_dim: 512
  dim_feedforward: 3200
  nheads: 8
  lr: 1e-5
  kl_weight: 10
  backbone: resnet18
  camera_names: ['top']

Baseline 与演进路线：
  当前:   ACT (CVAE) — 已验证，成功率 100%（简化任务）
  短期:   ACT + 分阶段 — 每阶段独立训练 ACT 实例
  中期:   Diffusion Policy — 多模态动作分布建模更强
  远期:   VLA (Vision-Language-Action) — 如 OpenVLA，接入语义指令
```

### 4.5 约束与降级层 (Guard)

```
模块名：    ActionGuard
职责：      对执行层输出的动作施加安全约束，在异常时触发降级
当前实现：  不存在

能力边界：
  V1（M2 目标）：
    ✓ 关节位置限幅
    ✓ 关节速度限幅
    ✓ 动作突变抑制（相邻步差值限幅）
    ✓ 异常动作拦截（NaN / Inf / 超大值）
    ✓ 触发日志记录
  V2（M3+ 目标）：
    ✓ 空间包络约束（铲斗不进入禁区）
    ✓ 负载上限估计（基于力反馈）
    ✓ 阶段相关约束（如 DIG 阶段限制回转速度）
  V3（远期）：
    ✓ CBF (Control Barrier Function) 安全滤波

输入：
  raw_action:    np.ndarray(action_dim,)   # 策略输出的原始动作
  S_t:           StructuredState           # 当前状态
  phase_label:   str                       # 当前阶段

输出：
  clipped_action: np.ndarray(action_dim,)  # 校验后动作
  guard_info:     dict                     # 触发标志、裁剪量、日志
  halt_signal:    bool                     # 是否触发停机

Baseline：
  V1 实现为纯 numpy 规则层，无额外依赖：
    def guard_v1(raw_action, prev_action, joint_limits, vel_limits, jerk_limit):
        action = np.clip(raw_action, joint_limits.low, joint_limits.high)
        delta = action - prev_action
        delta = np.clip(delta, -jerk_limit, jerk_limit)
        action = prev_action + delta
        return action

约束参数（excavator_simple，需根据 MJCF 确认）：
  joint_limits:   swing [-π, π], boom [-1.2, 0.5], stick [-1.5, 0.2], bucket [-1.5, 0.5]
  vel_limits:     各关节 ±2.0 rad/s

## 7. 关键设计决策记录

### D1: 为什么选择"分阶段 ACT"而非"单一长序列 ACT"？

- 完整挖掘循环约 1000-2000 步，远超 ACT 验证过的 chunk_size（100 步）。
- 各阶段动力学差异大（入土高阻力 vs 空载回转），单一策略需要覆盖多模态分布。
- 分阶段后，每个 ACT 实例只需覆盖 100-300 步的同质动作，学习难度显著降低。
- 阶段切换由规则 FSM 管理，可控性强，失败时易定位到具体阶段。

### D2: 为什么 MuJoCo 阶段的工作不浪费？

- 策略架构（ACT + action chunking）在 MuJoCo 上验证后，迁移到 Chrono 时模型结构不变。
- 工程流水线（录制/训练/评测/Guard/状态接口）对后端透明。
- 唯一需要重做的是数据采集——因为动力学分布改变了——但采集脚本也已解耦。

### D3: 为什么 Guard 优先于土体仿真？

- Guard 是所有后续工作的安全底线。即使在 MuJoCo 简化环境中，策略也可能输出非法动作。
- Guard 的工程量小（纯 numpy 规则），但收益大（防止仿真崩溃、提供可分析日志）。
- 在引入土体仿真后，Guard 的重要性更高（土体阻力可能导致动作超限）。

### D4: state_dim=4 在挖掘循环中是否足够？

- 当前 4-DOF（swing, boom, stick, bucket）覆盖了挖掘机上车的核心自由度。
- 对于当前阶段（仿真闭环验证），4-DOF 足够表达完整挖掘循环。
- 真实挖掘机额外包括行走（履带）和可能的延伸臂，这些属于后续阶段扩展。
- 扩展时 state_dim 从 4 增加到 6-8，ACT 模型仅需调整 state_dim 参数并重新训练。

## 9. 总结

当前技术路线的核心支撑——ACT 模仿学习框架和 MuJoCo 快速迭代环境——已经过验证且工程基础扎实。主要挑战集中在两个方向：

1. **纵向深入**：从刚体代理任务过渡到真实土体物理，这需要引入 Chrono DEM 等土体仿真后端。
2. **横向展开**：从单一策略覆盖全过程过渡到分层/分阶段架构，这需要引入 Phase Router、Guard、State Interface 等工程模块。

两个方向可以并行推进：M1-M2 聚焦横向展开（在 MuJoCo 上完成架构搭建），M3 聚焦纵向深入（引入 Chrono 土体并在新架构上训练）。这样既保证了每周有可展示增量，又为后续的高保真仿真和实机迁移打下了工程基础。
