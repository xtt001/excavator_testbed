# 关于智能挖掘机遥操作 Testbed 建设与传输优化路线的思考汇报

---

## 一、 为什么现阶段必须依赖 Testbed 进行数据采集？（长远战略考量）

目前我们可以直接在本地收集数据，且引入 Testbed（Python 与 AGXUnity 交互）客观上增加了一定的系统复杂度和时延。但从长远的技术演进来看，**现阶段重兵投入 Testbed 建设不仅是必要的，更是不可逾越的必经阶段**。核心原因有三点：

1. **Sim2Real（仿真到现实）的低成本试错闭环：** 智能挖掘机的终极目标是实车部署。但真实挖掘机（重载、破坏力大、环境危险）的试错成本极高。如果在未经闭环验证的情况下，直接让模仿学习模型（如 ACT）去控制实车，一旦模型输出异常动作（如铲斗砸向驾驶室），后果不堪设想。Testbed 为我们提供了一个高度逼真的物理交互沙盒（土体形变、动力学响应），让我们能够以极低的成本跑通 **“人工遥操作采集 -> 模型训练 -> 模型自主挖掘验证”** 的全链路闭环。
2. **构建一致的数据规范与管道：** Testbed 承担着统一数据规范的核心作用。无论是现在的仿真控制指令，还是未来的实车 CAN 总线指令，Testbed 能够帮我们在早期确立一套标准化的 HDF5 数据落盘格式和采集 Pipeline。
3. **提前暴露并解决部署期的“暗雷”：** 实车部署必然面临通信受限、画质压缩等恶劣条件。Testbed 在现阶段客观上存在的时延和渲染瓶颈，恰好为我们提供了一个真实的“压力测试”环境。如果在 Testbed 中我们都无法解决数据被污染的问题，实车部署必然失败。

## 二、 当前 Testbed 时延与未来真实 G2G 时延的“物理构成与等效性”

我们在 Testbed 中遇到的时延，与未来真实 5G 场景下的时延在**底层物理成因上截然不同，但在对“人机交互行为的畸变”与“数据污染效果”上是完全等效的**。具体组成梳理如下：

### 1. 当前 Testbed 的时延链路（算力与 I/O 瓶颈）
目前我们的链路为：`Python -> [Socket, ~6MB raw RGB] -> Unity FixedUpdate -> Python`。这里的 RTT 主要由本地系统的开销构成：
* **TCP 传输开销：** 随原始无压缩图像大小线性增长的传输耗时。
* **物理引擎步进时间：** Unity (AGX) 每一帧进行物理碰撞解算与渲染的 FixedUpdate 耗时。
* **内存拷贝：** 图像数据在进程间的大量内存分配与拷贝。
* **OS 调度：** 操作系统的进程调度抖动。

### 2. 未来真实部署的 G2G (Glass-to-Glass) 时延链路（编解码与网络瓶颈）
未来部署到实车后，链路演变为：
* **摄像头曝光采集 -> H.264/H.265 硬件编码 -> 5G/4G 网络空口传输 -> 接收端硬件解码 -> 屏幕渲染**。

### 3. 两者的等效性结论
虽然前者是因为“数据太胖挤在本地管道”，后者是因为“压缩解压和网络波动”，但**它们最终在操作员端产生的现象是一致的——“推了摇杆，画面滞后”**。这种现象会诱发操作员放弃连续操作，转为“移动并等待（Move-and-wait）”甚至“反向过度纠偏”。
**因此，我们现在针对 Testbed 时延研发的“动作提纯”与“前馈补偿”机制，未来可以直接无缝平移至真实 G2G 场景。**

## 三、 遥操作的不可替代性与“模拟传输受限”的必要性

### 1. 为什么遥操作是技术路线上的必须？
挖掘作业是一个高度**非结构化、强物理耦合**的任务（土堆的软硬、石块的分布完全随机）。传统的 Rule-based（基于规则或轨迹规划）算法无法胜任。AI 必须依赖大量包含了“人类直觉、肌肉记忆和物理交互边界”的专家示教数据，才能通过模仿学习真正掌握挖掘技能。因此，遥操作是当前最高效、最核心的高质量专家经验“捕获器”。

### 2. 为什么我们现在就必须在 Python 端（受限视角）进行操作？
如果在 Testbed 阶段，我们让操作员直接看着 0 延迟、无损高清的 Unity 上帝视角窗口进行操作，将会引发灾难性的后果：
* 专家看着高清画面做出了极其完美的避障或精准切入动作。
* 但未来实车上的 AI，输入端只有经过高度压缩、存在噪点和延迟的摄像头 2D 画面。
* 如果把专家的完美动作，强行配对给 AI 的模糊视角进行训练，就会引发模仿学习中最致命的 **“观测不匹配（Observation Mismatch）”与“因果混淆”**。AI 会试图在模糊的画面中寻找导致那个动作的原因，最终学到错误的物理规律。

**因此，我们必须在数据收集源头，强迫操作员与未来的 AI 看同样的“受限/降级”画面，实现人机观测视角的绝对对齐。**

## 四、 核心优化目标梳理与“不可能三角”的打破

基于上述背景，我们当前的系统设计面临四个核心维度的需求，并呈现出经典的“不可能三角”矛盾：

1. **数据收集效率：** 需要能够高效、稳定地在本地将高频多模态数据（图像、控制指令、状态）同步落盘。
2. **操作员体验与沉浸感：** 需要极低的操作时延和高流畅度，避免眩晕和手抖。
3. **数据收集质量：** 画面必须保留铲斗、土体交互面的高频几何特征（AI 学习的必需品）；且必须保证人机观测同源，消除因果错位。
4. **数据规范化：** 保证整个 Testbed 提供标准化的、可直接无缝喂给 ACT 模型的统一格式。

**核心矛盾（不可能三角）：** 追求**操作体验（低延迟）**往往需要全局高倍压缩视频，这直接伤害了**数据质量（AI 特征丢失）**；而追求**数据质量（高清无损）**则会引发严重的传输滞后，反过来破坏操作员体验，导致落盘的动作轨迹充满噪音。

**我们的破局思路（当前正在做的优化方案的价值）：**
为了在不伤害任何一角的前提下实现闭环，我们提出的“任务感知协同框架”是目前最优的解法：
* **ROI 动态编码：** 我们牺牲无关背景（天空、远景），死保核心区（铲斗、作业面）画质。以此在极低带宽下，同时保住了**低延迟操作体验**和**高保真数据质量**。
* **AR 预测性前馈：** 在物理时延无法进一步压榨时，通过渲染零延迟的 AR 铲斗虚影，在视觉上“欺骗并补偿”操作员。在不增加通信负担的情况下，极大提升了**操作体验**，并从源头抹平了错误纠偏的动作噪音，提纯了**数据质量**。

**总结：** 我们现在在 Testbed 阶段死磕“传输优化、ROI、AR”，绝不是在做无用功，而是在搭建一套能在未来极其恶劣的实车网络环境中，依然能为具身智能源源不断输送高质量、纯净、因果对齐数据的“最强炼丹炉”。
